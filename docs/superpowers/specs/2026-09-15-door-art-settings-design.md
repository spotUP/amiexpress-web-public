# A door setting whose value names its art

## 1. Why

The sysop asked to "wire up the request door and all other of our TypeScript
doors to the ANSI Studio when applicable". Investigation moved the target:

- **The TypeScript doors have no ANSI art to wire.** All 42 of them draw
  through the SDK's widget engine in code. Across the whole `Doors/` tree the
  only art assets are `super-qix`'s 16 `.ans` game backgrounds and REQUESTS'
  28 files - and REQUESTS is a C door, not a TypeScript one.
- **The Studio's door-art mechanism only addresses a SECTION INSIDE A CONFIG
  FILE.** `artSections` in a manifest names `{file, section}`, and
  `readDoorArtSections` cuts the named block out of an Empire-format cfg. Art
  that IS a file has no representation at all.
- Exactly one door declares art today: `Doors/emp_tools` (Bulls' title logo,
  JoinCnf's banner).

So REQUESTS' bulletin art - the header and tail the requests screen is drawn
between, plus 20 alternate designs inherited from the classic Request door -
cannot be opened in the Studio, and the artists who draw this board's screens
have no way to reach it.

## 2. Decisions taken (sysop, 2026-09-15)

1. **Scope: board-facing art only.** REQUESTS' bulletin header and tail and
   their alternates. `super-qix`'s backgrounds stay out - they are assets the
   game draws, not screens a caller reads, and filling the artists' Studio
   with game scenery is not what was asked for.
2. **Model: two slots with a picker**, not twenty-two editable files. The
   Studio shows what the door USES; the alternates are a "use this instead"
   choice. A flat directory listing would make editing an unused alternate
   look identical to editing the live screen.
3. **Declaration: the SETTING is marked as art-valued.** REQUESTS already has
   `BulletinHeader` and `BulletinTail` settings whose values name the files.
   The picker is therefore the setting itself, and no filename is written down
   twice.

Decision 3 is the one worth defending. The alternative - a separate
`artSections` entry per file - would state each filename in two places, and
this repository has spent the last two days paying for exactly that shape: a
screen classed as art in one table and generated in another, a
`door.settings.json` hand-edited while `settings.c` generated it, a door
binary whose source was current and whose bytes were not.

## 3. Architecture

Three layers change, each in one place.

### 3.1 Declaration - the C settings DSL and the manifest

`sdk/c/include/ae_settings.h` gains one macro beside the nine it already has:

    AE_SETTING_ART(key, label, def, cfgkey, help)

It emits an ordinary `type: "string"` setting with `"art": true` added, so a
door that declares one gets BOTH the admin form field (which is what writes
the value) and the Studio slot, from a single declaration.

`sdk/c/examples/requests/settings.c` changes two lines: `bulletinHeader` and
`bulletinTail` become `AE_SETTING_ART`. `bulletin` does NOT - it names the
screen the door WRITES, a destination rather than a drawing.

`Doors/REQUESTS/door.settings.json` is regenerated by `make -C sdk/c settings`.
It is generated output; it is never hand-edited (that mistake was made and
caught by the drift guard on 2026-09-15).

### 3.2 The schema, which is where this silently fails

`SettingSchema` in `web/backend/src/doors/door-settings.service.ts:210` gains:

    art: z.boolean().optional(),
    artMaxLines: z.number().int().min(1).max(100).optional(),
    artMaxLineLength: z.number().int().min(1).max(1000).optional(),

**This is not optional housekeeping.** Zod strips unknown keys, so a manifest
carrying `art: true` against today's schema loses the flag between the file and
every reader, and the Studio shows nothing with no error anywhere. A board
setting on this project has three homes - the form, the cfg mapping and the
schema - and the schema is the one that fails quietly.

`artMaxLines` / `artMaxLineLength` are the editor's limits, the same two the
`artSections` path already carries - where they are REQUIRED. On an art
setting they are optional, because a door that simply wants its art editable
should not have to invent numbers; omitted, they take the schema's own ceilings
(100 lines, 1000 columns), which is what an unconstrained canvas already is.

### 3.3 Resolution - a slot's value becomes a path

`/api/door-art` (`web/backend/src/api/door-art-routes.ts`) today lists the
manifest's `artSections`. It gains a second kind of slot, built from the
settings where `art === true`:

    slot.id        the setting's key            (e.g. "bulletinHeader")
    slot.label     the setting's label          ("Bulletin header art")
    slot.file      the setting's CURRENT value  ("Bulletin_Header.txt")
    slot.rows      lines in that file
    slot.choices   art files found in the door's folder

Reading and writing a file-backed slot replaces the Empire section cut with a
whole-file read/write, latin1, through the same endpoints and the same
`DoorArtDialog` canvas. The C64 and Teletext variants keep their present home,
`Screens/doors/<COMMAND>/<slot.id>.<variant>.ans`, keyed by the setting's key
instead of a section name.

**Paths.** `ArtSectionSchema.file` is `BARE_FILE_RE`
(`/^[A-Za-z0-9_-][A-Za-z0-9._-]*$/`) - bare names, no directories. REQUESTS'
alternates live in `headers/` and `bulletindesign/`, so an art setting's value
must be allowed ONE subdirectory level and no more:

    /^[A-Za-z0-9_-][A-Za-z0-9._-]*(\/[A-Za-z0-9_-][A-Za-z0-9._-]*)?$/

No `..`, no leading `/`, no drive or assign (`BBS:`), no backslash. The
resolved absolute path is then re-checked to be inside the door's own
directory before any read or write - the regex states the intent, the
containment check is what enforces it, and a bug in one is not a hole in both.

**Candidates.** `slot.choices` is the art files in the door's directory and its
immediate subdirectories, by extension (`.txt .ans .ansi .asc .ascii`), each
with its line count so the Studio can show what a choice costs.

### 3.4 The Studio

`DoorArtDialog` and the `ScreenEditor` canvas are unchanged - a file-backed
slot arrives as the same base64 latin1 body. The door-art card gains, for an
art setting only: the current filename, its row count, and a **Choose another**
control writing the setting through the settings save path that already exists.

Deliberately NOT built: a "-> 13 request rows fit" hint. That arithmetic is
REQUESTS' alone (a 23-row budget, less header, less tail) and would put one
door's rules in shared UI. The card shows row counts; the setting's help text
explains the budget.

## 4. Error handling

| Case | Behaviour |
|---|---|
| Setting names a file that does not exist | The slot lists with `missing: true` and its row count absent. The Studio offers the picker, not the editor. Never a 500. |
| Value escapes the door directory | Refused at the schema and again at the containment check; 400, and the value is not written. |
| Door declares `art` on a non-string setting | Manifest rejected by the schema refinement, as `choice` without `choices` already is. |
| Art file is not valid latin1 / is enormous | Existing door-art limits apply unchanged. |
| Two doors share one directory (`emp_tools` is B and J) | `commands` on the setting already scopes it, exactly as for settings and art sections today. |

## 5. Testing

**C (`sdk/c`)**: `AE_SETTING_ART` emits `art: true` and an otherwise ordinary
string setting. The existing byte-compare in
`web/backend/tests/doors/c-sdk-settings-manifest.test.ts` then covers REQUESTS'
regenerated manifest for free, across all three C doors, because it reads
`SETTINGS_DOORS` from the Makefile.

**Backend**: an art-valued setting appears in `/api/door-art` with its current
file and row count; a read/write round-trip preserves bytes including ESC and
high-bit; `../` and `BBS:` values are refused and nothing is written; a missing
file reports `missing` rather than failing; a `.choices` list finds the
alternates one level down.

**Admin**: the card shows the filename and rows; choosing another writes the
setting; the editor opens the file the value names.

Each of these fails before the change and passes after - the backend ones by
construction, since no art-valued setting exists today.

## 6. Out of scope

- `super-qix`'s 16 backgrounds, per decision 1.
- Any TypeScript door: none has art to declare. When one gains some, this
  mechanism already covers it - that is the point of marking a setting rather
  than listing files.
- The remaining 14 manifests have not been audited for art embedded in their
  cfg files (the `emp_tools` case). That is the existing `artSections`
  mechanism, needs no new code, and is worth its own pass.
- Uploading a NEW art file through the Studio. The picker chooses among files
  the door ships; creating one is the file manager's job.
